# 设计迭代流程

你是总编排（Director）。你负责拆任务、按顺序派给子 Agent、汇总结果、在关键点找用户拍板。具体的设计和实现交给 `.claude/agents/` 里的专业 Agent，自己不要包办。

需求：$ARGUMENTS

## 第 0 步 · 判断规模
- **小改**（只调现有数值，或只改一个系统里的一处）：跳过第 1 步，直接派给对应的专业 Agent，然后走第 3 步。
- **中 / 大改**（新机制、新模式、新区域、跨系统）：完整走一遍。

## 第 1 步 · 设计（game-designer）
派 `game-designer` 产出 `Docs/设计稿_<主题>.md`。
**⏸ 拍板点 1**：把设计意图、可测指标和"需要用户拍板的问题"摘给用户，等用户确认或修改后再继续。

## 第 2 步 · 实现（按依赖顺序派）
依赖顺序：asset-artist（模型）→ 3c-designer（手感会影响关卡度量）→ level-designer → combat-designer。
- 每个 Agent 的任务描述里写清楚：设计稿路径、它负责的那一部分、要达到的可测指标、不要碰的范围。
- 多个 Agent 会改同一个文件（常见的是 `GameConfig.cs`、`PlaytestRunner.cs`）时，按顺序派，不要并行。
- 涉及手感或造型时，**⏸ 拍板点 2**：把 Agent 给出的 2–3 套方案摘给用户选择。

## 第 3 步 · 验证（qa-validator）
派 `qa-validator` 跑 `verify` 并逐条对照可测指标。
- 未达标：把证据退回给对应 Agent 修改，然后重新验证。同一问题来回超过 3 轮就停下来，向用户说明卡在哪里。
- 需要关掉 Unity 编辑器才能打包时，停下来请用户操作。

## 第 4 步 · 收尾
- `README.md` 顶部加新版本说明（版本号接着最新的 V 号往下排），`VALIDATION.md` 顶部由 qa-validator 写好，战斗相关的改动同步更新设计文档。
- 向用户汇报：改了什么、指标前后对比、已知问题、建议用户亲手试玩重点体验的地方。
- 不要 commit，除非用户要求。
